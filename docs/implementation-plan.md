# Relay runtime 实现方案

日期：2026-11-04。目标是会话会合、密文转发、资源保护与清理。
协议、客户端包和 Bun runtime 已实现；本文保留实现约束，运行入口见[运行说明](runtime.md)。

## 1. 首版范围

使用 Bun 实现单实例 WSS 服务，两端均主动连接。
同一服务入口处理最小会合请求、WebSocket 和健康检查，使用运行时原生升级与二进制接口。
HTTP 框架仅在实际路由复杂度需要时引入，不预建管理 API、插件框架或存储适配层。

首版不建设设备登记库、独立许可后端、租户管理、管理 CLI 或计费系统。
用户凭证服务保持独立；数据转发不访问账号服务或数据库。
文件落点见[文件组织](repository-layout.md)。

## 2. 会合与生命周期

会合层只需要解决：两端如何找到同一入口、验证连接到正确会话、同时就绪并安全结束。

- 在线映射仅表达当前可达连接，随连接失效回收；建立或替换映射需验证控制权，不能只看公开标识。
- 待接入会话、角色和凭据均有界。凭据绑定所属会话、角色、运行时范围与有效期，不能跨会话使用。
- 同一数据会话每个角色只有一条有效连接；重复接入或凭据重放不得替换已经接通的对端。
- 双端接收器就绪、限制一致后才进入 ready；提前到达的数据不得被当作已建立通道。
- 单进程内接入和关闭按会话串行决定；跨异步操作返回后重新检查该会话是否仍有效。
- 关闭统一取消定时器、移除映射和监听、结束相关 socket，并释放一次资源占用。
- 重启使用新的运行时代际；旧会话、凭据和迟到回调不能恢复已结束的连接。

数据会话可概括为 `waiting → ready → closed`，等待期间也可因取消、过期或容量不足结束。
桌面在线入口与待接入数据会话分别设定存活规则，不能让待接入超时误关健康在线入口。
连接/会合超时及初始容量见[运行配置](runtime.md#3-运行限制与观测)，生产容量仍需压力验证。

客户端保存配对及必要的再次会合信息；断线后更新临时连接和凭据。
会合消息和在线入口恢复已在 R2 固定；两端产品接入需持久保存入口信息，做到重启后重连无需重新扫码。

现有 `RelayReady` 仅包含版本、sessionId、ownerEpoch 和 limits。
客户端必须匹配自己已确认的会话选择；形状校验本身不能验证对端身份。
本地 harness 只模拟 ready 和转发，不提供上述生产会合保护。

## 3. 二进制帧与流控

复用当前协议包的 v1 布局。每个 WS binary message 恰好一帧，网络字节序，头长 24 字节：

| 偏移 | 长度 | 字段                           |
| ---- | ---- | ------------------------------ |
| 0    | 1    | version = 1                    |
| 1    | 1    | type：1 DATA / 2 ACK / 3 CLOSE |
| 2    | 2    | flags，必须为 0                |
| 4    | 8    | uint64 seq                     |
| 12   | 8    | uint64 cumulativeBytes         |
| 20   | 4    | uint32 payloadLength           |

DATA 为 1–65536 字节，序号从 1 开始，每方向的序号和累计字节必须连续。
ACK 无载荷，只能确认已发送的真实帧边界；完全相同的 ACK 可忽略，倒退、越界或字节数不符则关闭。
CLOSE 计数为零，载荷为最多 256 字节的枚举原因 JSON。
大计数用 bigint，进入 JSON 时显式编码，不能丢失精度。

现有端侧限制：

| 项目                            | 当前值      |
| ------------------------------- | ----------- |
| DATA 载荷                       | 最多 64 KiB |
| 每方向未确认字节                | 256 KiB     |
| 每方向未 ACK 帧                 | 最多 1024   |
| 待发送队列                      | 2 MiB       |
| 接收队列 / 原生 socket 发送缓冲 | 各 1 MiB    |
| 队列项数                        | 最多 1024   |
| 有待处理数据但无 ACK / 排空进展 | 最多 15 秒  |

发送队列容纳现有 1 MiB 上传加密后的额外头/tag。端侧限制不等于服务端队列限制或进程 RSS。
runtime 转发前也要校验帧、方向计数、速率和缓冲预算，不能相信客户端声明的容量或伪造 ACK。

ACK 表示字节已被有界接收流接纳，不代表命令执行或文件持久化。
密文关闭 WebSocket 压缩，消息上限必须覆盖 65536 字节载荷和 24 字节头。
Bun 原生发送返回 -1 时数据已入队，等待排空再发后续帧；非空帧返回 0 则结束失败流，不能静默丢帧或重发。

当前不增加延时合并策略，优化须按[性能方案](performance-and-operations-plan.md)实测。

## 4. 两端接入

桌面把 RelayStream 接入现有 `acceptSecureChannel` 和配对/业务入口；
App 交给 `connectSecureChannel`，继续校验已知桌面身份。
首次配对按已有的身份确认与桌面批准流程进行，runtime 不替桌面批准访问。

客户端由一个连接 owner 管理 direct/relay 选择、取消、退避重连和生命周期。
关闭某条传输路径不删除配对，也不误关另一条路径。
断线重建 Noise；有副作用的业务请求由既有命令回执或恢复协议处理，Relay 不负责重试。

实现前刷新桌面/App 目标分支和共享包版本，复用已有连接管理组件。
当前桌面协议已有 QR v3 direct endpoints 和二进制上传；
Relay 候选、邀请信息和持久化迁移需同步检查双端兼容性，不能把 Relay URL 塞入 IP 字段。

## 5. 验收与后续

R2 验证正常会合、错会话/错角色、凭据过期或重放、重复接入、取消、ready 竞争和迟到关闭。
同时覆盖非法帧、伪造 ACK、慢读、原生缓冲上限、实例容量拒绝和循环建连后的资源回收。

R3 在真实 Electron/iOS/Android 和至少两个网络完成配对、配置导入、已配对重连及桌面撤销配对。
服务重启后恢复会合，手机换网或前后台切换后只有一个有效连接 owner。
自建交付阻断 Cherry 官方服务后仍可完成上述闭环，见[自建方案](open-source-deployment.md)。

现有 proof transcript 和签名 helper 是可选工具，不要求为它们建设 challenge/登记服务。
未来确定需要额外接入策略时再选择使用；当前基础会合 API 见[控制协议](runtime.md#2-最小会合)。
