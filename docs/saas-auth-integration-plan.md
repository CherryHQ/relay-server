# 可选用户策略接入边界

日期：2026-11-04。本文只保留未来确有需要时的接入原则。
基础 Relay 和免费托管均不以用户登录、设备归属后台或收费系统为前置；尚无此类生产集成。

## 1. 用户体系与 runtime 解耦

企业与个人 SaaS 按统一产品体系演进，登录、账号会话、组织和后台权限由原服务负责。
Relay 不复制这些模型，不处理产品 refresh token，不直读账号数据库，也不在逐帧转发中调用认证服务。

设备身份、Noise、配对和业务权限继续由桌面/App 执行。
同账号、同组织或获准使用中转，都不代表已经取得桌面的业务访问权。

基础 runtime 只需验证会合凭据和运行资源限制。
原来的设备登记接口、Relay 管理后端、租户字段、授权账本和后台 CRUD 不再列为首版待建模块。

## 2. 确有业务策略时再接入

例如部署者需要限定成员使用，才增加一个明确的接入判断。
上层使用现有用户体系作决定，将受约束的会话许可或限制交给 runtime；
runtime 只关心当前连接是否允许，不依赖用户服务的内部表或角色模型。

这项集成可以选择受信签名许可或独立适配器，具体方式随实际需求确定。
产品账号 token 不发给任意 Relay；客户端自报的账号、角色或套餐不能成为可信依据。
已有 proof 编码与签名 helper 可按需采用，不要求为它们预建 challenge/登记服务。

启用某项策略时，需同时定义其有效期、已有连接如何失效和依赖故障行为；
策略不可用不能静默绕过。上述能力只约束选择了该策略的部署，不改变基础自建能力。

## 3. 收费与交付

免费提供可作为运营选择，前提是实际成本可接受。运行限额和防滥用始终存在。
套餐、用户余额、计费账本、全局预算预扣不进入当前协议或实现顺序。

若将来需要收费或企业管理，在对应业务服务中实现，再通过接入策略影响资源使用。
不因预留这种可能性，就提前建设独立 Relay 管理平台或要求两端登录。
